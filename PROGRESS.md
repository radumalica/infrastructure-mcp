### 2026-07-23 — internal/ssh
- `Pool`: connection cache keyed by inventory server name (`map[string]*ssh.Client`, mutex-guarded), `Run(ctx, server, command)` returning stdout/stderr/exit code/duration, `Close()`.

User request: many older switches/routers in the target environment have obsolete SSH crypto stacks (or no SSH at all — Telnet only), and none support public-key auth. Building this ahead of the v0.7 (Networking) schedule since it's foundational transport work, not vendor-specific tooling.

New `Target` type + `(inv *Inventory) Target(name)` unifies lookup across servers/routers/switches into one connection-level shape, so the transport layer doesn't care which inventory category a name came from. Ambiguous names (same name in two categories) are rejected with `ErrAmbiguousTarget` rather than silently picking one.
- `internal/ssh`: `Pool.dial` now resolves via `inv.Target()` instead of `inv.Server()` — this is what let routers/switches (not just Linux servers) reuse the entire existing pooling/proxyjump/host-key machinery for free. New `applyLegacyCrypto()` widens the negotiated key exchange/cipher/MAC/host-key algorithm sets using `golang.org/x/crypto/ssh`'s `InsecureAlgorithms()`, additively (never replacing the modern defaults) and only when `Target.LegacyCrypto` is true — verified this API exists via `go doc` on the actual installed module rather than assuming.
- Backward compatible by construction: existing `Server`-only inventories and all prior `ssh` package tests pass unchanged, since `Target()` for a `Servers` entry reproduces exactly the old `Server`-based behavior (protocol implicitly ssh, `LegacyCrypto` false).
- Tests: `internal/inventory/target_test.go` (resolution across all 3 categories, ambiguity, default protocol, invalid protocol validation), `internal/ssh/legacy_test.go` (algorithm widening, non-mutation of package globals), `internal/ssh/pool_test.go` additions (a `Switches`-sourced target with `LegacyCrypto: true` dials successfully through the fake SSH server; a `telnet`-protocol target is refused by `ssh.Pool.Run`).
### 2026-07-23 — Legacy network device connectivity, part 2: Telnet transport + dispatcher (feature complete)
- `internal/telnet`: minimal RFC 854 client. `iac.go` implements a small state machine (`iacFilter`) that strips Telnet option-negotiation sequences from the byte stream and replies by refusing every option (WILL→DONT, DO→WONT), keeping the session in plain character mode — state persists correctly across reads, since a negotiation sequence can straddle two `Read()` calls (tested explicitly). `client.go` drives login (wait for a login/username prompt, send user, wait for a password prompt, send password, drain post-login banner/MOTD and detect a re-shown login prompt as `ErrLoginFailed`) and command execution. Telnet has no protocol-level "command finished" signal (unlike SSH's exec channel + exit-status), so command completion is inferred via an **idle timeout**: keep reading until no new data arrives for `idleTimeout` (default 2s) or `commandTimeout` (default 30s) is hit. `pool.go` caches one session per target (serialized per-session, since Telnet is a single raw stream with no SSH-style channel multiplexing) with `PoolOption`s mirroring `ssh.Pool`'s shape (`WithDialTimeout`, `WithLoginTimeout`, `WithIdleTimeout`, `WithCommandTimeout`). `Result` has an intentionally-always-zero `ExitCode` and always-empty `Stderr` — documented as a Telnet protocol limitation, not a bug. 85.6% coverage; tests include a real login+command round trip against an in-process fake Telnet server (mirrors the `internal/ssh` fake-server testing pattern) plus dedicated IAC state-machine tests (plain passthrough, escaped 0xFF, negotiation reply content, negotiation split across reads, subnegotiation block discarding).
- `internal/remote`: thin composer — `Pool.Run` resolves the target's `inventory.Protocol` and dispatches to an `sshRunner` or `telnetRunner` (both small interfaces so dispatch logic is unit-tested with fakes, no real sockets needed), translating `telnet.Result` → `ssh.Result` so callers keep using the one shape they already know. Deliberately depends on interfaces rather than concrete `*ssh.Pool`/`*telnet.Pool` types — lets `pool_test.go` verify routing (server→ssh, modern router→ssh, telnet-flagged router→telnet, error propagation, `Close()` closing both) without any network I/O.
- `cmd/server`: now constructs `ssh.Pool` + `telnet.Pool` + `remote.Pool`, and passes `remote.Pool` (not the raw `ssh.Pool`) to `RegisterRunCommand` and `linux.New` — **zero changes needed in `mcp/tools` or `internal/linux`**, since `remote.Pool.Run` has the exact same `(ctx, target, command) (ssh.Result, error)` signature their existing `CommandRunner`/`Runner` interfaces already expected. This is the payoff of having built those as small interfaces back in v0.1.
- `configs/inventory.example.yaml`: added a Telnet-only router (`legacy-edge`) and a legacy-crypto switch (`ancient-sw`) so the feature is discoverable from the example config, not just from code.
- **Feature complete at the transport layer.** `run_command` now transparently reaches old Telnet-only and legacy-SSH-crypto network devices, exactly as it does modern Linux servers — no tool-layer changes were needed, only the transport layer underneath. `uptime`/`disk_usage`/`memory_usage` are *not* meaningful against network gear (they shell out to `/proc` and `df`, which don't exist on Cisco/vendor OSes) and remain Linux-only; vendor-specific device diagnostics are out of scope here and belong to v0.7 (Networking) if pursued later. `internal/ssh.buildAuthMethods` now also registers `ssh.KeyboardInteractive` alongside `ssh.Password` whenever a password is configured — many old network-vendor SSH stacks (e.g. Cisco IOS) only offer the "keyboard-interactive" auth method, not "password", and password-only auth would silently fail to authenticate against them. Verified end-to-end with a fake SSH server that offers *only* `KeyboardInteractiveCallback` (`TestPool_Run_KeyboardInteractiveOnlyDevice`), not just unit-tested in isolation. Also strengthened `internal/telnet`'s bad-credentials test: the fake server now keeps the connection open and re-shows the login prompt after a failed auth (as real devices do) instead of closing it, so the test actually exercises the intended `ErrLoginFailed` detection path instead of passing on an incidental EOF.

### 2026-07-24 — v0.2: Linux extended tools (failed_services, cpu_usage, reboot_required, running_processes, journal_errors, kernel_version)
- `internal/linux`: six new `Client` methods, each a thin wrapper around one portable-ish shell command plus a dedicated parser in `parse.go`, following the exact pattern established by `Uptime`/`DiskUsage`/`MemoryUsage` in v0.1.
  - `FailedServices` (`systemctl list-units --type=service --state=failed --no-legend --plain`), `RunningProcesses` (`ps -eo ... --sort=-pcpu | head -n N`), `JournalErrors` (`journalctl -p err -n N -o json`, parsed as newline-delimited JSON — journald's actual wire format, one object per line, not a JSON array), and `KernelVersion` (`uname -r`) depend on **systemd + GNU/procps** rather than only `/proc`/POSIX `df`, unlike v0.1's tools. This is a deliberate, documented departure from v0.1's portability-first choices: these facts (failed units, journal, `ps --sort`) don't exist in a portable form on non-systemd/non-GNU systems. On Alpine/busybox or non-systemd hosts these commands fail and the tool surfaces the existing structured error envelope — not a crash, just a documented gap. `uname -r` and `ps` are broadly portable; `systemctl`/`journalctl`/`sort -V`/GNU `ps` flags are the systemd/GNU-specific parts.
  - `CPUUsage` samples the aggregate `cpu ` line of `/proc/stat` twice, one second apart, in a single remote command (`sh -c 'cat /proc/stat; sleep 1; cat /proc/stat'`) to keep both samples on one round trip. **Caught by advisor review before commit**: the initial implementation summed all 10 `/proc/stat` fields (including `guest`/`guest_nice`) into `total`, double-counting CPU time the kernel already folds into `user`/`nice` — since this project's roadmap explicitly targets Proxmox/KVM hosts, where guest time is a large fraction of total CPU, this would have meaningfully inflated reported usage on exactly the hosts that matter most. Fixed to sum only indices 0-7 (`user`..`steal`); regression test `TestParseCPUUsage_GuestNotDoubleCounted` asserts a nonzero-guest sample produces the same result as the zero-guest case.
  - `RebootRequired` combines the Debian/Ubuntu `/var/run/reboot-required` marker file with a running-vs-newest-installed-kernel comparison (`uname -r` vs. the highest `/boot/vmlinuz-*` by version sort) — best-effort on distributions that don't use that naming convention (empty "newest kernel" is a valid, non-error result, not treated as a mismatch).
  - `RunningProcesses`/`JournalErrors` take a `limit` parameter, clamped server-side (`clampLimit`: default when `<=0`, capped at a max) before being embedded into the command via `%d` — safe because it's a validated integer, not string interpolation of untrusted input, consistent with README's no-shell-interpolation rule.
- `mcp/tools`: six new tools (`failed_services`, `cpu_usage`, `reboot_required`, `running_processes`, `journal_errors`, `kernel_version`), all sharing the extended `LinuxDiagnostics` interface, `withLogging`, and `toolerr.Wrap` machinery from v0.1 — no changes needed to the logging/error-contract infrastructure itself. `cpu_usage` reuses `severityForPercent` at the same warn/crit shape as disk/memory (80%/95%); `failed_services`/`reboot_required`/`journal_errors` use a simpler present/absent → warning/ok status since they're not percentage-based.
- Tests: `internal/linux/parse_test.go` and `client_test.go` extended with the same table-driven/fake-runner style as v0.1's tools (including the CPU guest-time regression test above); `mcp/tools/diagnostics_test.go` extended with one MCP-protocol round-trip test per new tool plus severity-table coverage for `cpu_usage`, and the existing `TestDiagnosticsTools_ErrorPath` now covers all 9 Linux diagnostic tools, not just the original 3. 88.3% coverage on `internal/linux`, 97.5% on `mcp/tools`.
- `cmd/server/main.go`: wired all six new tools alongside the existing three; zero changes to the dependency graph itself since they all hang off the same `linuxClient`.

### 2026-07-24 — v0.3: Docker (docker_ps, docker_logs, docker_stats, docker_restart, docker_images)
- **CLI-over-SSH, not the Docker Engine API.** New `internal/docker` package runs `docker` CLI commands over the existing `remote.Pool` (the same SSH/Telnet transport `internal/linux` uses), rather than talking to the Docker Engine API remotely over TLS. Chosen because: (1) there's no dedicated Docker inventory category or API-token/TLS-cert fields in the README's inventory shape — Docker targets are just existing `servers` that happen to run the daemon; (2) it lets `docker.Client` reuse 100% of the already-built pooling/proxyjump/host-key/legacy-crypto machinery for free, exactly like `internal/linux` did; (3) `docker.Runner` is the identical `Run(ctx, server, command) (ssh.Result, error)` shape as `linux.Runner`, so `remote.Pool` satisfies it with zero adapter code. The README's architecture note mentions API tokens living inside adapters (true for Grafana/Proxmox, planned in later versions) — that pattern still applies there; Docker is the exception because it's colocated with a Linux host we already reach over SSH, not a separate networked service.
- **`docker ps`/`docker images`/`docker stats --no-stream` all use `--format '{{json .}}'`**, parsed as newline-delimited JSON (one object per line, not a JSON array) — the same pattern `internal/linux.JournalErrors` established for `journalctl -o json` in v0.2. Far more robust than parsing Docker's human-readable table columns.
- **Input validation is the load-bearing security property of this feature.** Unlike v0.1/v0.2's tools (server name only, resolved through the inventory, never concatenated into a command), `docker_logs`/`docker_stats`/`docker_restart` take a user-supplied `container` string that gets embedded into a remote shell command. `internal/docker/validate.go`'s `validateContainerRef` whitelists Docker's own container/image naming pattern (`^[a-zA-Z0-9][a-zA-Z0-9_.-]{0,127}$`) and is called *before* any container reference is formatted into a command string — never after. `tail`/`limit`-style integers are still embedded via `%d` on a validated `int`, consistent with v0.2. Added a new `toolerr.CategoryInvalidInput` (+ `toolerr.ErrInvalidInput` sentinel) since none of the existing 5 categories fit a validation failure. Tested at three levels: `validateContainerRef` unit tests (rejects `;`, `|`, `$()`, backticks, spaces), `docker.Client` tests (validation blocks the call before any `Runner.Run`), and one true end-to-end test (`TestDockerLogs_RejectsShellInjection` in `mcp/tools/docker_test.go`) that drives a real `*docker.Client` (backed by a `Runner` that fails the test if ever called) through the actual MCP protocol with a shell-metacharacter container name and asserts the client sees `category: "invalid_input"` — proving the guard is wired end-to-end, not just present at each layer.
- **`docker_restart` is the tool surface's first destructive, named action** (as opposed to `run_command`, which is inherently unconstrained). Implements README's "dangerous actions require confirmation" via a `confirm` bool input: without `confirm: true` it returns `status: "confirmation_required"` and does not call `docker.Client.Restart` at all (verified by asserting the fake diagnostics layer was never invoked); this is the pattern intended for future v0.x mutating tools (`docker_stop`, Kubernetes rollouts, etc.) to copy rather than reinvent.

- **Honest scope note on parsing accuracy, mirroring the self-signed-TLS/ticket-auth callouts on v0.6's Proxmox entry: Cisco IOS CLI output has no formal machine-readable spec to verify against**, unlike Grafana/Proxmox's documented HTTP APIs (which were verified via Context7 before writing code). Parsers target the four commands' long-stable plaintext conventions — the `<hostname> uptime is ...` line and `Cisco IOS Software, ...` banner from `show version`, the fixed `show ip interface brief` column layout (with `show inventory`'s `NAME:`/`DESCR:`/`PID:`/`VID:`/`SN:` block format) — the same conventions every major network automation tool (Netmiko, NAPALM, RANCID) has relied on for decades, and unit-tested against representative canned output, **not verified against a live Cisco device** (none available in this environment). `cisco_backup` (raw `show running-config`) and `cisco_logs` (raw `show logging` lines) sidestep the risk entirely by not parsing structure out of the output at all.
- `show ip interface brief`'s `Status` column can be one or two words (`up` vs `administratively down`); the parser treats everything between the fixed-position `Method` and trailing `Protocol` fields as `Status` rather than assuming a fixed column count, so multi-word statuses don't get truncated or misaligned.
- Tool input field is `device` (not `server`, `target`, or `instance` like other adapters) since these tools address routers/switches specifically, not the generic multi-category "target" concept `internal/remote` operates on internally.
- Tested with a fake `CommandRunner`/`VendorLookup` pair (no real SSH/Telnet connection, same shape as other adapters' fakes) plus table-driven parser tests against realistic sample IOS output for all four `show` commands. `internal/cisco` 92.2% coverage, `mcp/tools` 97.4%.
- README: v0.7 Roadmap entry split — Cisco's bullet list moved to Current Features, MikroTik/UniFi remain listed as not started; `internal/cisco/` un-marked `# planned` in the architecture tree.
- **Command-rejection detection can't rely on exit codes, because Telnet has none.** `internal/telnet.session.run` never sets an exit status (there's no such concept in a raw Telnet CLI session), and even over SSH, IOS often returns exit code 0 for a command it refused. A real failure mode this catches: a Telnet/SSH credential without enable/privilege-15 running `cisco_backup` would get IOS's `% Invalid input detected ...` line back as if it were a config dump, with no non-zero exit to signal anything went wrong. Fixed by scanning every command's stdout for IOS's `% ...` rejection prefixes (`invalid input detected`, `incomplete command`, `ambiguous command`, `authorization failed`, `access denied`) regardless of exit code, surfaced as a new `cisco.ErrCommandRejected` sentinel classified in `toolerr` as `auth` (the most common real cause is an under-privileged session).
- **`cisco_backup`/`Client.Backup` documented as returning only the first page on a paginating device.** `internal/ssh`/`internal/telnet` run one command per session with no setup step, so there is no way to send `terminal length 0` before `show running-config` — unlike Netmiko/RANCID, which do this as standard session setup. Rather than silently truncating a "backup" at IOS's `--More--` prompt, this is called out explicitly in both the `cisco.Client.Backup` doc comment and the `cisco_backup` tool description, so an agent (or operator) knows to configure `terminal length 0` on any device this tool targets. Not fixed at the transport layer in this PR — that would mean giving `internal/ssh`/`internal/telnet` a multi-command-per-session primitive, a bigger change than this vendor adapter warrants on its own.
- **`cisco_logs` no longer counts `show logging`'s config-summary header block against `limit`.** The command's output opens with `Syslog logging: enabled ...` / `Buffer logging: level ...` lines before the actual buffered messages; originally `parseLogs` treated every non-empty line as a message, so `limit: 5` on a device with a short header could return mostly header noise and few real messages. Now skips every line until the first one matching IOS's `%FACILITY-SEVERITY-MNEMONIC:` message marker (present on every logged line whether or not `service timestamps log` is configured). Also corrected the `limit` field's jsonschema description, which claimed "most recent first" while the parser has always returned messages in their original oldest-to-newest order (only which lines are kept was ever reversed, not their order) — reworded to match actual behavior instead of changing the ordering, since chronological order is more useful for reading a log tail.
- Full local gate re-run clean: `gofmt`, `go build`, `go vet`, `go test ./... -race -cover` (all green); `golangci-lint` not installed in this environment, so it could not be re-run here — flagging for CI to catch instead.

### 2026-08-03 — operator-features: `docker_exec`

User asked for a batch of operator-facing improvements proposed after a full documentation read (README, ADRs, PROGRESS.md, memory). First landed: `docker_exec`, the container-scoped equivalent of the existing top-level `run_command` tool — `docker exec <container> sh -c '<command>'` over the same `internal/remote.Pool`-backed `Runner` interface `internal/docker`'s other methods already use.

- **Deliberately not confirm-gated**, unlike `docker_restart`. `run_command` itself — the tool this mirrors — has never been confirm-gated despite being able to run anything on a whole server; gating `docker_exec` but not `run_command` would be an inconsistent, false sense of safety. Confirm-gating in this codebase is reserved for a single *named* destructive action (`docker_restart`, `proxmox_start_vm`/`stop_vm`/`snapshot`), not for "arbitrary command" tools.
- **A non-zero exit code is data, not an adapter error** — same reasoning as `run_command`'s `exit_code` field: a command run inside a container (e.g. `grep` finding nothing) can legitimately fail without the exec mechanism itself failing. This is a deliberate divergence from `Restart`/other docker methods, which do treat non-zero exit as an error, because those methods invoke one specific docker subcommand whose failure always means something went wrong, whereas `Exec`'s payload is an arbitrary user command.
- **Free-form command text is shell-quoted, not whitelisted** — `internal/docker.shellQuoteSingle` wraps the command in single quotes (escaping embedded `'` as `'\''`) before embedding it as the single argument to the container's `sh -c`, so it reaches the remote command as one opaque string regardless of contents. The container reference itself still goes through the existing `validateContainerRef` whitelist pattern unchanged.
- Tests: `internal/docker/client_test.go` (adapter-level, including an embedded-single-quote regression test) and `mcp/tools/docker_test.go` (MCP-protocol round-trip, non-zero-exit-is-not-an-error, adapter-error path). ### 2026-08-03 — operator-features: `cisco_backup` pagination fix (Telnet only)

Partial, honest fix for the pagination limitation this project's own PROGRESS.md already flagged when Cisco (v0.7) shipped: a device whose page length isn't already unlimited would silently return only the first `--More--` page of `show running-config`.

- **Researched before writing any code** (this project's standing rule for anything touching real device/vendor behavior, same as the Grafana/Proxmox API verification): confirmed via web search that Netmiko — the reference network-automation library — always disables IOS paging by driving a *persistent* interactive shell session (`terminal length 0` sent, then read, then the real command sent on the same session), never via one-shot non-interactive exec. This directly explains why the original limitation was real, not a guess.
- **Telnet-connected devices are fixed for real, not just documented**: `internal/telnet.Pool` already keeps one persistent session per target across `Run` calls (see its own doc comment) — so `Backup` now sends `"terminal length 0"` as its own call, then `"show running-config"` on the same underlying session, and the setting genuinely carries over. - **SSH-connected devices are NOT fixed, and this is a deliberate scope boundary, not an oversight**: `internal/ssh.Pool.Run` opens a brand-new exec channel per call, and Cisco IOS's terminal/pagination state does not survive across separate exec-channel invocations (the same reason Netmiko never uses one-shot exec for this) — so sending `terminal length 0` as its own `Run` call over SSH would set it on a channel immediately torn down, accomplishing nothing. Fixing this for SSH too would mean adding a persistent interactive (PTY) session primitive to `internal/ssh` — a bigger, riskier change than this fix warrants on its own, especially with no live Cisco device available in this environment to verify PTY/interactive-shell behavior against (same "don't guess unverifiable device behavior" posture as the original v0.7 Cisco PROGRESS.md entry). `Backup`'s doc comment now explains both halves explicitly instead of a single blanket caveat.

### 2026-08-03 — operator-features: audit history MCP resource (`audit://recent`)

Adds `internal/audit` (a small, fixed-capacity, in-memory ring buffer of `Entry{Timestamp, Tool, Target, User, Status}`) and `mcp/resources` — this project's **first MCP resource**, as opposed to tool. Adds a no-argument, read-only tool validating the inventory file itself, distinct from every other tool (which validates one target's reachability at call time).

- **Discovered while designing this that `inventory.Load` already fails the whole server startup on any missing `${VAR}`** (see `internal/inventory/expand.go`'s `expandEnv`) — so "check every referenced env var is set" against the *already-loaded, in-memory* inventory would be a no-op: if the server is running at all, every env var it started with was set. Re-scoped the tool to **re-read and re-parse the inventory file from disk on every call** instead of reusing the shared `*inventory.Inventory` every other tool gets — this is what makes the tool actually useful: it catches drift since the server started (an env var later unset from the environment, a config file hand-edited but not yet reloaded, a key file rotated out from under a still-valid-looking path), not just a redundant re-check of what's already known to be fine.
- **SSH key and kubeconfig file readability aren't covered by `inventory.Validate()`** (which only checks struct-level required-field/format rules, e.g. `Key string` has no `validate` tag at all) — this tool is the first thing in the codebase that actually opens those files to confirm they're readable, mirroring `internal/ssh/auth.go`'s own `expandHome`+`os.ReadFile` sequence (duplicated as a 6-line unexported helper here rather than exporting `internal/ssh`'s version, since the two packages have no other reason to depend on each other).
- **Reports every problem found in one pass**, not just the first — `Problems []string` accumulates across every server/router/switch/kubernetes entry, so an operator fixing a broken inventory doesn't have to fix-and-rerun once per problem.
- `.golangci.yml` gained one more narrow G304 exclusion (`mcp/tools/check_inventory_health.go`), same operator-controlled-config-path precedent as `internal/inventory/loader.go`/`internal/ssh/auth.go`/`internal/backupstore/store.go` above.
- Tests: healthy case, missing env var, unreadable SSH key, unreadable kubeconfig, malformed YAML, and missing inventory file — all via the real MCP protocol against real temp files (`t.TempDir()`), not mocks.
- Full local gate green: `gofmt`, `go build`, `go vet`, `go test ./... -race -cover`, `golangci-lint run ./...` (0 issues).

## Decisions & Deviations from a literal README reading

- **Module path**: used `infrastructure-mcp` (no VCS host) since this repo has no git remote configured yet. Rename in `go.mod` once the real module path (GitHub org/repo) is decided — this will require updating all internal import paths.
- **Server auth validation**: not enforced at the inventory layer (see above); the SSH adapter is responsible for producing a clear error if a target ends up with no usable credential at connection time.
- **Env-var expansion scope**: applied over raw file bytes before YAML parsing, so it also matches `${...}` inside comments. Documented rather than fixed with comment-stripping (adds complexity for a case unlikely to occur in real files).
- **"user" in structured logs**: no auth/identity layer exists yet, so `user` is populated from the connecting MCP client's self-reported `ClientInfo.Name` rather than an authenticated identity. Revisit when/if auth is added (not currently on the README roadmap for v0.1-v1.0).
